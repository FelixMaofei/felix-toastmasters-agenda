# 自然语言与受控执行工作流

适用 WorkBuddy、Codex 和其他能执行本地命令的 Agent。模型负责理解用户、映射本期变化和判断信息重点；程序负责时间计算、确定性排版和文件导出。不因模型不同而预设它只能做机械提取。

Skill 内置官方 Logo 和可分发字体。正常工作不联网，也不让模型每期重写 CSS。

## 三阶段不是三道审批门

先检查当前消息、图片、附件和文件名。已有事实不再问。再按完整俱乐部名称查找 profile；没有旧会单或 profile 也要继续初始化。

用户只需要经历：

1. 必要信息一次确认；
2. 直接看到 A4 图片初版；
3. 一句话修改或直接交付。

第一阶段先说明已识别内容和整体进度，再把真正影响会议承诺的缺项一次问完。必要问题与可选增强分开，提供可直接照抄的回答格式；最后补一句“是否还有其他希望呈现在会单上的？”，用少量例子带出候选内容。不要一次问一个、让用户逐个点选，也不要把字段名扔给用户。

当前消息或 profile 已经明显暴露必要缺项时，立即提问并结束本轮；不要先建任务、读 `input-schema.md` / `agenda-rules.md`、查看脚本帮助、计算整场时间或创建文件。星期只有用户提供或程序验证后才显示。当前明确事实覆盖 profile，不向小白解释 profile 差异或更新命令。

必要信息答完后，在同一轮连续执行计算与视觉初版，不再要求用户先阅读整篇 Markdown 并回复“确认”。图片出来后，才让用户选择修改或直接交付。

## 绝对不要做

- 不要求用户自己写 JSON；
- 不要求每期提供旧会单；
- 不手算开始时间、结束时间、转场或剩余分钟；
- 不让用户选择 renderer、模板、CSS 或 Python 权限；
- 不把会议类型、时长或剩余面积当作版式路由；
- 不把内部文字稿变成第二次用户审批；
- 不在必要信息已经齐全后继续追问可选项；
- 不用图片模型重排会单文字，也不生成或修复二维码；
- 不用宽泛主目录搜索寻找 Skill、profile 或历史会单；
- 当前消息明显有真实缺项时，不先检查源码和运行环境。
- 普通会单制作直接运行已安装脚本，不浏览、解释或修改源码，不做开发级测试；只有命令真实报错或用户明确维护 Skill 时才进入代码。
- 普通会单制作不加载 V3 架构、视觉合同或命令帮助；这些只服务维护者。

## 第一阶段：必要信息确认与计算

先从材料识别内部 `meeting.json` 所需事实：

- `meeting`：期数、日期、正式开始/结束、本期地点、主题、今日一词、会议经理、会长；
- `roles`：接龙中真实出现的功能角色，保留顺序；
- `prepared_speeches`：每篇将演讲者、题目、时长、同编号点评人放在同一对象；
- `impromptu`：即兴主持、即兴点评人；用户没给时长就保留 `null`；
- `backstage`：拍照、场控/PPT、投票链接等，不进时间轴；
- `special_segments`：工作坊、微课等本期特殊环节，必须有负责人、时长和相对位置；
- `participant_pathways`：仅在用户提供真实 Pathways 进展时，用姓名映射到 `PM L1` 等文字。

接龙明确顺序优先。若自动环节与接龙顺序不同，用 `agenda_overrides.after` 表达；不要改源码或接受错误顺序。

真正需要先问的通常只有：俱乐部身份/实际时间地点无法判断、已出现角色缺负责人、特殊环节缺负责人/时长/位置、流程存在两个冲突理解、或计算后必须确认超时。主题、今日一词、Pathways、介绍、二维码等通常列为可选增强，不阻断初版。

缺项存在时不创建文件。回答齐全后再写 `meeting.json` 并直接进入第二阶段。只有内部字段确实无法表达时才读 [输入结构](input-schema.md)。

Python 不可用时，先保留已识别的会议事实并用人话说明“当前电脑暂时不能完成可靠的时间重算”；不要把未经计算的手排时间冒充闭合会单。

## 第二阶段：快速生成视觉初版

必要信息齐全后，只发一句进度：“信息已齐，正在计算和排版；下一条直接给 A4 图片初版。”然后只运行：

```bash
python3 "$SKILL_DIR/scripts/run_agenda.py" first meeting.json \
  --club-profile "俱乐部完整名称" \
  --output-dir output
```

`first` 一次完成事实计算、内部 Markdown、默认视觉意图和 HTML/PDF/PNG 初版。不要再读取架构、视觉合同、命令帮助、computed 字段或中间 Markdown。退出 `2` 时只按返回的真实错误提问；退出 `0` 直接看图。

必须打开真实 `agenda.preview.png`，检查整页层级、主流程原始字号、负责人列、对齐、裁切、重叠、空卡和组件内部死空白。直接把预览给用户；自动检查通过不等于用户已经认可。

Chrome/Chromium 不可用时，文字会单仍然有效；保留它并给一个最短环境建议，不交付未经真实渲染的视觉成品。

## 第三阶段：修改或立即交付

图片初版后只问一次：“这版可以直接导出；你也可以一句话修改。”同时告诉用户：

- 可改：姓名和角色、时长与顺序、环节开关、显示列、重点、字号、组件和介绍；
- 固定底线：一页 A4、官方 Logo、时间闭合、不裁切隐藏；
- 内容变化会重新计算；纯视觉变化只重新排版。

用户说“直接导出”“生成吧”“OK”“可以”“就这样”时立即运行：

```bash
python3 "$SKILL_DIR/scripts/run_agenda.py" final output/agenda.preview.html \
  --output-dir output
```

收到上述指令后只运行这一条命令，不读文件、不建任务、不讨论 profile。必须看到 `ok: true`、`stage: finalized` 和 `pages: 1`。最终 PNG 必须与预览字节一致，再交付 PDF/PNG。`final` 不读取 meeting JSON，不重新计算，不改变 HTML，也不应再次启动浏览器渲染。

## 用户要求调整时

- 时长、负责人、名称、开关、转场和顺序属于内容变化，写入 `agenda_overrides` 后重跑 `first`；
- “字大一点”“重点弱一点”“俱乐部介绍放后面”属于视觉变化，只改 `agenda.view.json` 后重跑 `preview`；“加入 Pathways 列”只有已有真实 Pathways 数据时才是视觉变化，否则先补内容事实；
- “负责人没对齐、有死空白、列宽难看”是 renderer 问题，不给 view 增加字段，也不让用户授权改技术；
- 纯视觉调整前后，计算结果中的姓名、顺序、时长、地点和正文必须一致；
- 如果一页装不下，保留上一份可用成品，只给 1-2 个业务取舍选项。

## 完成回复

最终只说明：会单已完成、时间是否闭合、本轮变化是否落实，并交付 PDF/PNG。不要向普通用户展示 JSON、HTML、profile 路径、技术阶段或检查日志。用户说“OK”“就这样”表示停止继续改版。只有长期设置确实更新成功时，才说“以后默认沿用”。
