# 整体架构

这套 Skill 的重点不是让每个 Agent 都读懂全部业务和排版代码，而是让每一部分只做好自己最擅长的事。这样换到 Codex、WorkBuddy 或豆包 Work 时，用户体验和最终结果仍然稳定。

```text
用户的角色接龙和本期变化
        ↓
Agent 理解事实、一次问清
        ↓
程序继承稳定资料、重新计算并检查
        ↓
Renderer 排成一页 A4
        ↓
交付层原样提供 PNG 和 PDF
```

## Agent：理解用户并推动流程

Agent 负责用户真正需要语言理解的部分：

- 从文字、图片和附件中识别已有事实；
- 区分俱乐部长期稳定内容与本期变化；
- 发现会改变流程、负责人或时间的缺项，并一次问清；
- 把确认后的事实整理成内部 `meeting.json`；
- 根据用户的自然语言修改内容或视觉效果；
- 调用 `first` 或 `final`，向用户展示实际结果。

Agent 不手算时间，不自行决定特殊环节的位置，也不让用户配置模板、列宽或 CSS。普通任务只读 `SKILL.md`；字段确实不清楚时才读 `references/input-contract.md`。

## 程序：保证事实和时间可靠

业务程序负责所有可以确定计算的事情：

- 读取俱乐部 profile，并让本期明确事实优先；
- 根据角色是否出现，决定相应环节是否出现；
- 绑定演讲与点评，支持半分钟时长和非默认顺序；
- 检查特殊环节的真实负责人、时长和相对位置；
- 自动分配可伸缩环节，让会议重新闭合；
- 对无法闭合、需要准确超时确认或内容过密的情况明确报错。

程序只在用户明确说“以后都这样”时更新长期 profile。本期日期、角色、临时地点、特殊环节和临时时长不会静默变成长期默认。

## Renderer：只负责把确定内容排好

Renderer 接收已经计算完成的会议事实和受控的视觉意图，负责：

- 使用官方 Logo、离线字体和统一视觉系统；
- 在同一视觉系统中适应普通例会、重点环节或演讲密集场景；
- 调整字号、重点、留白和对齐；
- 生成一页 A4 HTML，并检查裁切、隐藏和溢出。

Renderer 不能改姓名、顺序、正文和时长。视觉修改与会议事实分开保存，因此重新计算内容时可以继续沿用用户已经确认的视觉偏好。

## 交付层：用户看到什么，就交付什么

`first` 串起业务计算、排版和真实浏览器导出，一次生成匹配的 HTML、PDF 和 PNG，并记录文件指纹。

`final` 只检查这些预览文件仍然完整，然后把现有 PDF 和 PNG 原样提升为交付文件。它不重新计算、不重新排版、不再次调用浏览器，因此不会出现“预览是一版，最终文件又变了”的情况。

如果当前版本检查失败，程序不会用坏文件覆盖上一份可用成品，而是把具体问题交还给 Agent 用人话说明。

## 资料分层

- `SKILL.md`：每次执行必须知道的流程和边界。
- `references/input-contract.md`：只有字段表达不清楚时才读取。
- `docs/architecture.md`：维护者理解当前职责边界时按需读取。
- 历史 V3 教学资料保存在本地归档，不随 V4 安装包或公开仓库分发。
- `tests/`：把确定性业务规则和已知异常案例固定下来，避免把长禁令重新塞回 Skill。

这种分工减少了不同 Agent 自由发挥造成的差异：Agent 只承担理解与沟通，计算、排版底线和原样交付由同一套程序保证。
